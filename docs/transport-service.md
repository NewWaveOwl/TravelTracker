# Independent Transport service (#36)

`TravelTracker.Transport.Api` owns Transport entries and Route Points on port 5105. Api references only its own Data/Domain and shared Security; Data references its own Domain and EF/Npgsql. The host starts independently, while protected operations require the live Users HTTP contract and its separate credentials. `TravelTracker.Api` is now a library of remaining unimplemented service interfaces, with no runnable catalogue endpoints. Shared Trip domain snapshots remain in the historical Domain project; they are not persisted Transport entities.

## Startup and migrations

Supply `ConnectionStrings__Transport` through local environment configuration or user secrets, pointing at a dedicated PostgreSQL database. Supply `Authentication__Bearer__Authority`, `Issuer`, and `Audience` for the chosen provider as described in [authentication](authentication.md), plus `Users__InternalBaseUrl` (HTTPS Users API base URL) and `Users__ServiceAccessToken` (a backend token scoped to `users.access` whose subject is in the Users API `UsersAccess:AllowedServiceSubjects` allowlist). The guided Supabase launcher supplies the Users values. Never commit credentials.

Set `Database__ApplyMigrations=true` to apply the committed Transport migrations at startup. Alternatively use `dotnet ef database update --project src/TravelTracker.Transport.Data` with the connection configured. `Database__SeedExamples=true` optionally inserts the original six mode examples (including bike) and three location examples into empty resource tables. Stable sample UUIDs are preserved. Initialization never clears saved data; seed operations are transactional. Only one service instance may initialize/issue identities at a time. Apply the PrivateRoutePoints migration before starting this version. The previous host can only read shared entries through a compatibility view. A downgrade of the schema is refused while private route points exist.

Run `dotnet run --project src/TravelTracker.Transport.Api --launch-profile http`. `/health` is anonymous and returns service `TravelTracker.Transport`; Development Swagger is available at `/swagger`. Health reports host liveness, not database readiness. The Blazor client's Transport URL remains `http://localhost:5105`; its existing saved sample lookup stays compatible when examples are enabled. Other hosts can remain stopped.

### Rolling out private route points

Apply the Transport migration before routing writes to the upgraded API. During the handover an older host can continue to serve shared reads through the legacy `RoutePoints` view. The migration transaction backfills existing points as shared and installs the view atomically. If runtime and migration roles differ, grant the old runtime role SELECT on the compatibility view and verify that the new runtime role retains its required table privileges. Drain old writers before enabling new writers because the ID allocator is single-instance. The old route-point creation API cannot create private points through the view.

For an application rollback, leave the migrated database in place. The older binary can only read the shared catalogue. Use a forward fix to restore private-point functionality. A schema downgrade checks for private rows under a table lock and refuses the change when any exist. If only shared records exist, the downgrade restores the original table and identifiers.

## HTTP selection and security

Existing POST and GET-by-ID routes and camelCase DTOs remain unchanged. New collection routes return saved records as JSON arrays:

- `GET /api/v1/transport-modes?code=bike&name=bike`: optional exact lowercase supported mode and trimmed case-insensitive name substring.
- `GET /api/v1/route-points?type=transport_stop&name=station`: optional exact lowercase location type and the same name filtering.

Omitted filters return every visible record; no matches return `200 []`. Order is ordinal case-insensitive name, then public UUID. Repeated filter parameters or unsupported nonempty code/type return 400. All detail/collection GET operations use named `CatalogueRead` (`catalogue.read`); POST uses `CatalogueWrite` (`catalogue.write`). Missing/invalid bearer tokens return 401, insufficient scopes 403. Every protected request also checks the validated `(iss, sub)` against the live Users service over HTTPS using the separate `users.access` credential, whose service subject must be allowlisted. Active accounts may read shared entries and their own private route points. An active account with write scope may create a private route point. Creating shared modes or directly creating a shared route point requires an active administrator. Banned, deactivated or unknown accounts receive 403, and Users lookup failures fail closed with 503. New route points default to private visibility and use the user ID resolved by the Users service. POST /api/v1/route-points/{id}/share publishes an owned point. An existing shared point returns the same 200 response with shared visibility. Another account’s private point returns 404. The PrivateRoutePoints migration preserves the previous catalogue as shared and keeps all UUIDs and trip references. Health remains public and does not call Users. Existing create validation rejects unsupported code/type, blank names and out-of-range coordinates before storage. Unknown write fields retain the previous framework behavior (ignored). SourceId remains unverified GUID metadata with no cross-service lookup or foreign key. Transport entries and locations carry no schedule, departure/arrival or boarding times.

Internal bigint keys are application-issued, never exposed in HTTP, and rebuilt above the largest key in both tables after restart. Public UUIDs remain stable. This allocator supports one Transport process; multiple writers require a separate node-aware allocation change. PostgreSQL checks enforce supported codes/types, nonblank names and coordinate ranges; public UUIDs are unique per resource. Storage conflicts return 409, known constraint failures 400, transient outages 503, unexpected storage errors 500, without provider details.

## Verification

`tests/TravelTracker.Transport.Api.Tests` owns moved HTTP/bearer tests and new selection/persistence tests. Application tests replace only storage with isolated EF InMemory; production has no in-memory provider switch. Signed RSA JWTs go through the production bearer handler and discovery stub. Tests cover issuer/audience/signature/expiry and correct/incorrect scopes, plus live standing and role enforcement, validated identity forwarding, Users service credentials, and fail-closed dependency errors; anonymous health remains explicit.

Run `dotnet test TravelTracker.Tests.slnx --configuration Release --filter "Category!=PostgreSQL"`. For migrations, constraints, failed-write emptiness and host restart persistence, set `TRAVELTRACKER_TEST_POSTGRES` to an isolated PostgreSQL instance with CREATEDB, then run with `--filter "Category=PostgreSQL"`. Each relational test creates and drops only its randomly named disposable database. PostgreSQL tests fail when configuration is absent; they never fall back to InMemory.

## Frontend selection (#44)

The Blazor **New Trip** page uses this service's authenticated collection, detail and creation routes through a dedicated frontend `TransportClient`. Saved transport entries appear as directly selectable cards without a transport search step. Selecting one opens the map for choosing saved departure and destination endpoints; location name/type filters and a list alternative remain available. Authorized creation forms and an ordered editable draft chain retain public IDs. The map reuses the Attractions screenshot as an illustrative background and retains selected markers when filters or views change. It does not provide live street tiles, geocoding or arbitrary map-pin creation. Manual-coordinate creation remains available to write-capable sessions. A location enters the chain only after it has a saved public ID.

The frontend exposes an ordered `SelectionChanged` callback with public transport, departure and destination DTO snapshots and optional traveller-entered travel/change minutes for the future trip editor. Both endpoints are required and re-read by public ID before confirmation. No trip or scheduled journey is saved. Catalogue records do not provide travel/transfer durations; the separate review panel accepts these as explicit planning inputs only, without adding fields to catalogue HTTP requests. Change minutes apply after their transport and count toward the total only when another draft entry follows. See [implementation and verification](issue-44-implementation.md).
