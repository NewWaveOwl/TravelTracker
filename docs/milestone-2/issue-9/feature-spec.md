# Attraction management and name search specification

Confirmed planning deliverable for [#9](https://github.com/NewWaveOwl/TravelTracker/issues/9), published in [feature issue #15](https://github.com/NewWaveOwl/TravelTracker/issues/15). The human answered the priming interview on 2026-10-06 and expanded the feature to attraction management and name search. Build a standalone Attractions API on port **5104**, using C# and ASP.NET Core on **.NET 10**, with seeded in-memory data. Implementation uses **VS Code with GitHub Copilot**.

## Attraction representation

All successful list, detail, create and update responses use these camelCase fields. Optional values appear as `null` when unavailable.

| Field | Type and meaning |
| --- | --- |
| `attractionId` | GUID string, generated by the server on creation; immutable |
| `name` | Required attraction name |
| `description` | Nullable text describing the attraction |
| `rating` | Nullable manually entered decimal score from 0 to 5; no external ratings provider |
| `address` | Address text |
| `lat`, `lon` | Decimal coordinates |
| `estimatedVisitMinutes` | Integer visit duration in minutes |

Seed examples include Montreal Museum, Science Centre and Old Port, with fixed GUIDs so demonstrations and tests are repeatable. POST generates a new GUID; PATCH preserves it. Map internal `Latitude`/`Longitude` properties explicitly to JSON `lat`/`lon`. The current shared Attraction model has no description or rating; the standalone service owns its expanded representation instead of migrating every service or adopting Id64.

## Endpoints

| Method and route | Behavior and success response |
| --- | --- |
| `GET /health` | `200 {"status":"ok","service":"Attractions"}` even when other services are stopped |
| `GET /api/v1/attractions` | `200` ordered array of all current records |
| `GET /api/v1/attractions?name=museum` | `200` ordered array of name matches |
| `GET /api/v1/attractions/{id}` | `200` attraction details |
| `POST /api/v1/attractions` | `201 Created`, saved representation and `Location: /api/v1/attractions/{generated-guid}` |
| `PATCH /api/v1/attractions/{id}` | `200 OK`, updated representation |

Unknown valid GUIDs return `404` for details and valid updates. Malformed GUIDs, JSON, field types or invalid field values return `400`. Validation failures use `application/problem+json` with field errors. No delete endpoint is requested.

## Create and update rules

The human confirmed that names cannot be empty or whitespace-only, ratings must be between 0 and 5 inclusive, and `null` means no rating. Create and update responses must reflect the saved state. In-memory changes survive later requests within the same running service and are lost when it restarts.

Use a create DTO containing only writable fields; the server generates `attractionId`. Trim names before storing. Omitted description/rating on creation become `null`. Search and list include newly created records and reflect updated names, ratings and descriptions.

### Binding and partial update decisions

These details complete the implementation contract; they are planning decisions rather than additional quoted human answers:

- PATCH uses a partial JSON object with the same writable field names, not RFC 6902 JSON Patch operations. Omitted fields retain their current values. Explicit `null` clears `description` or `rating`; it is invalid for name, coordinates, address or duration.
- Create requires `name`, `lat`, `lon` and `estimatedVisitMinutes`, avoiding accidental zero coordinates when values are missing. Omitted address becomes an empty string; a supplied address must be text. Duration is a nonnegative integer; latitude is within -90 to 90 and longitude within -180 to 180. Wrong types and non-finite numbers are invalid.
- An empty PATCH object, unknown fields or an attempted `attractionId` assignment returns `400`. Request DTOs must not allow the client to overwrite a server-owned ID.
- Validate the complete candidate record before saving. If any field fails, none of the requested updates are applied. Updating an existing record preserves its ID and all omitted fields.
- The store owns process-lifetime data, supports safe concurrent requests, and returns snapshots. Do not recreate it per request, expose mutable internal collections, or leave a multi-field PATCH partly applied.

## Name search

Trim the query and match a **literal case-insensitive substring of `name`**, using ordinal comparison for the in-memory catalogue. Missing, empty or whitespace-only input returns all records; no matches returns `200 []`. Order by name with ordinal case-insensitive comparison, then GUID as a deterministic tie breaker. Do not search descriptions/addresses or interpret wildcard/regex syntax. Let the HTTP framework decode once; do not decode again. Reject repeated `name` parameters with `400` rather than choosing a value silently.

The earlier proposed 100-character query bound is superseded by the human's revised search contract; this feature adds no such limit. Search itself must not mutate records.
