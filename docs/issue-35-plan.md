## Database decision and remaining approval

1. **Database provider — approved: PostgreSQL.** Use EF Core 10 with a compatible `Npgsql.EntityFrameworkCore.PostgreSQL` provider and committed PostgreSQL migrations. PostgreSQL is required for local durability demonstrations and relational verification; use an isolated local instance or disposable test database/container. Preserve decimal precision and public Guid identities with explicit PostgreSQL mappings, while keeping Domain free of provider dependencies. No SQLite fallback or untested multi-provider claim. Supply connection strings through environment-specific configuration; do not commit credentials. Server version and deployment configuration are not selected by this database decision. Reference: [Npgsql EF Core provider](https://www.npgsql.org/efcore/).
2. **Privacy/access scope — approved.** Implement creator-private/admin-shared Attractions. Owner identity comes only from validated `(iss, sub)`; active callers see shared plus their own private records; other people's private details/PATCH return 404, including for administrators. Visible shared writes by non-admins return 403; clients cannot set owners. Creation adds optional `visibility`, default private, with shared creation reserved for administrators. Live Users checks use the explicit configurable HTTPS consumer boundary in the service guide. There is no production bypass using client headers or stale token-role/status claims. The actual Users upstream implementation remains its owning issue's responsibility.

The implementation preserves the explicit independence boundary: the Attractions process, PostgreSQL store, health and Swagger run without starting another TravelTracker host. Protected operations intentionally require the configured live Users boundary and fail closed with 503 when it is unavailable. Tests replace that HTTP dependency, which proves the consumer contract and rules but not a complete deployed Users/frontend journey. No production account-standing bypass is provided.
